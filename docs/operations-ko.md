# Divercity Pay 운영 가이드

2026년 11월 22일 기준. 신청은 테스트용이며 결제와 지급은 시뮬레이터로 처리한다.

## 환경과 배포

1. Preview용 Supabase에는 가상 사용자와 계약서만 넣는다. Vercel Preview의 두 공개 Supabase 환경변수와 `PRODUCTION_SUPABASE_URL`을 설정한다. Preview 빌드는 운영과 같은 프로젝트 URL을 거부한다.
2. [README의 DB 순서](../README.md#데이터베이스-변경)로 빈 테스트 프로젝트를 구성한다. CI는 별도 PostgreSQL에서 전체 마이그레이션과 초안·검토·주문 회귀를 실행한다. 실제 Supabase의 Auth와 Storage는 가상 계정으로 추가 검증한다.
3. 신규 배포 전에 Preview에서 임차인·다른 임차인·관리자 계정을 각각 사용해 조회 범위를 확인한다. 관리자 TOTP 등록 및 재로그인, 소유자의 계약서 미리보기·다운로드, 타인 접근 차단, 만료 링크 재발급을 점검한다.
4. 운영 전환 시 웹과 SQL 버전을 맞춘다. `009–011`은 이전 웹 코드의 일부 조회와 쓰기를 차단한다. 운영 전환 전에 인증 연락 수단, 관리자 권한 복구 담당자, DB 백업과 계약서 백업을 확인한다. 변경 시간에 DB 적용과 웹 배포를 연이어 진행한다. Vercel 롤백은 SQL도 호환되게 복구할 절차와 함께 판단한다. [Vercel 배포 환경](https://vercel.com/docs/deployments/environments) · [Vercel 롤백](https://vercel.com/docs/instant-rollback)

## 관리자 접근 및 계정 복구

- 운영자는 개별 계정에 인증 앱을 등록하고 복구 연락 수단을 확인한다. 업무 종료·역할 변경 시 역할과 세션을 회수한다. 실사용자 정보를 받기 전에 공유 시연 계정의 권한을 회수한다.
- `/admin/operations`에서는 최근 상세 조회와 계약서 링크 발급을 확인할 수 있다. 링크 발급 시각은 파일 열람을 허용한 시각이다. 서명 URL·원본 계약서·전체 계좌번호는 채팅, 화면 공유 자료, 오류 로그에 남기지 않는다.
- Supabase Auth에서 서비스 도메인, `/login/recovery/update` 허용 리디렉션, Custom SMTP 발신자를 설정한다. 실고객 접수 전 가입 확인 메일과 재설정 메일을 수신 가능한 QA 주소로 시험한다. 링크를 처음 열었을 때와 만료·재사용했을 때를 각각 확인한다. 발신 도메인의 SPF/DKIM 및 429 제한을 함께 점검한다. [Supabase Auth SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

## 접수와 리뷰 이메일

- 운영자는 `/admin/operations`에서 신규·보완 제출을 잠시 중지할 수 있다. DB에서 새 제출을 막으므로 저장해 둔 초안과 이전 신청은 조회할 수 있다. 중지 사유, 시작 시각, 담당자, 다음 안내 시각을 운영 기록에 남긴다. 재개 전에 가상 신청 한 건의 제출 기록과 알림을 확인한다.
- 48시간 초과 미처리 건, 제출·파일 링크 오류 보고, 이메일 대기·실패, 계약서 보관량이 운영 화면에 표시된다. 외부 가동 상태 확인 도구는 개인정보를 반환하지 않는 `/api/health`를 호출하고 503을 담당자에게 알리도록 지정한다.
- 심사 이메일을 사용하려면 발신 도메인 검증 후 `REVIEW_MAIL_FROM`, `REVIEW_MAIL_SITE_URL`, `RESEND_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`을 서버 환경변수로 지정한다. 수신 가능한 QA 계정에서 확인한 뒤 `REVIEW_MAIL_ENABLED`와 DB의 `divercity_private.operating_settings.email_updates`를 활성화한다. 호스팅 플랜에 맞는 주기로 `GET /api/operations/review-mail`을 호출하고 Authorization Bearer에 `CRON_SECRET`을 사용한다. 현재 저장소에는 실행 스케줄이 지정되어 있지 않다. 발송사 접수 오류는 재시도되며 최종 실패는 운영 화면에서 확인한다. 발송사 접수 이후의 반송은 발송사 대시보드에서 확인한다. [Resend 이메일 API](https://resend.com/docs/api-reference/emails/send-email) · [Vercel Cron](https://vercel.com/docs/cron-jobs/manage-cron-jobs)

## DB와 첨부파일 복구 훈련

1. 격리된 테스트 환경에 가상 신청·계약서 한 건을 만든다. 신청번호, 계약서 경로와 체크섬, 상태 이력 수, 백업 시각을 기록한다.
2. 프로젝트의 DB 백업을 확보하고 비공개 `contract-documents`의 파일 원본을 별도 암호화 위치에 복사한다. 대상 경로와 메타데이터 목록을 함께 남긴다. DB 백업에는 Storage 원본 파일이 포함되지 않는다.
3. 새 격리 프로젝트에 DB를 복구하고 원래 경로에 파일을 복원한다. 원본과 체크섬이 일치하는지 확인한다. 관리자와 신청자가 복구된 상세·계약서·이력을 볼 수 있는지, 다른 임차인의 접근이 거부되는지 점검한다.
4. 복구 시간과 빠진 자료를 기록하고, 운영에 사용할 백업 주기와 복구 목표 시간을 정한다. [Supabase DB 백업](https://supabase.com/docs/guides/platform/backups) · [Storage 원본 복사](https://supabase.com/docs/guides/storage/management/download-objects)

## 월세 75만 원 지급 실패 연습

| 상황 | 운영자 조치 | 이용자에게 전달할 내용 |
|---|---|---|
| 결제 승인, 지급 결과 대기 | 하나의 신청번호로 결제와 지급 기록을 대조한다. 마지막 지급 결과와 확인 예정 시간을 기록한다. | 결제 상태, 지급 확인 중이라는 안내, 다음 회신 시각 |
| 결제 승인, 지급 실패 확인 | 실패 유형과 수취 계좌를 검토한다. 지급 재시도 또는 결제 취소 판단을 담당자가 기록한다. | 필요한 자료가 있는지, 다음 조치 및 예상 안내 시각 |
| 지급 완료 기록 확인 | 금액과 거래 참조번호를 대조하고 실제 완료 여부를 확인한다. | 확인된 지급 상태와 문의 번호 |

훈련에는 가상 월세 750,000원과 테스트 이용료 0원을 사용한다. 운영 비용표는 월세, 이용자 청구액, 임대인 지급액, 회사 부담액, 지급예정일 항목으로 관리하고 실제 요율·비용·환불 책임은 계약 확정 후 입력한다.

## 출시 전 확인 기록

- PostgreSQL 격리 테스트로 제출 재시도, 보완 전후 상태와 심사 이력, 관리자 권한, 계좌번호 컬럼 제한, 파일 접근 정책, 메일 대기열과 테스트 결제·지급 전이를 검증한다.
- 브라우저에서 가상 계정으로 iOS Safari와 Android Chrome의 파일 선택, 날짜 입력, 통신 중단·복구, 계약서 열기와 다운로드를 시험한다. 같은 신청을 두 창에서 수정·심사할 때 최신 이력과 충돌 안내를 확인한다.
- 운영 프로젝트에서는 별도 Auth·Storage 검증, 메일 실수신, 관리자 인증 앱 등록, 호스팅 권한과 알림 수신, DB 및 파일 복원 시험을 기록한 뒤 실제 신청을 받는다.
