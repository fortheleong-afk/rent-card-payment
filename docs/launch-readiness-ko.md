# Divercity Pay 실제 서비스 출시 준비

작성일: 2026-11-05. 이 문서는 개발 점검 자료이며 법률 의견이나 금융사 승인 결과가 아닙니다. 현재 서비스는 테스트 전용입니다.

아래는 11월 5일 초안의 기록입니다. 11월 22일 코드와 배포 준비 현황은 [운영 가이드](operations-ko.md)에 이어서 기록합니다.

## 1. 서비스 구조를 먼저 확정

- 임차인의 카드 결제부터 임대인 계좌 입금까지 자금 흐름을 도식화한다. 결제 가맹점, 계약 당사자, 자금 보유자, 실제 이체 실행자 및 정산 책임자를 명시한다.
- 임대인 별도 가입·사전 동의 없이 지급 가능한지, 계좌 명의와 계약상 임대인의 관계를 어떻게 확인할지 금융사 및 법률 전문가에게 확인한다. 이 서비스 모델에 대한 승인 여부는 아직 확인되지 않았다.
- 전자금융업 등록·면제 여부는 실제 수행 업무, 자금 이동 관여, 파트너 역할에 따라 검토한다. [전자금융거래법 제28조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1030749425). 과거 금융위원회 회신에서는 등록 면제 대상이 아니라면 송금·이체 서비스에 등록이 필요하다고 설명한다. [금융규제민원 과거 회신](https://better.fsc.go.kr/fsc_new/replyCase/PastReqDetail.do?actCd=R&muGpNo=88&muNo=117&pastreqIdx=1215&stNo=11). 과거 회신을 현재 모델에 그대로 적용하지 않는다.
- 현재 표시하는 2.9%가 단순한 테스트 가정인지 명시하고, 출시 전 수수료의 법적 성격·부담 주체·가격 표시를 검토한다. 여신전문금융업법 제19조는 신용카드가맹점의 가맹점수수료 회원 부담을 금지하므로, 현재 비용 구조가 어떻게 적용되는지 전문 검토가 필요하다. [법 제19조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029472861).
- 카드사·PG·은행과 서면으로 허용 업종, 외국인 및 해외 발급 카드 지원, 수취인 확인, 승인·취소·분쟁·정산 책임, 처리 시간과 한도를 확정한다.

## 2. 출시 차단 항목

1. **거래 무결성:** 지금 신청 금액·수수료·테스트 결제 상태는 브라우저에서 제출한다. 실제 서비스에서는 신뢰할 수 있는 서버에서 입력과 권한을 검증하고 수수료를 재계산해야 한다. 중복 요청 방지 키와 상태 전이 검증도 필요하다.
2. **상태 변경:** 관리자 상태, 이력, 알림이 별도 요청이며 알림 실패는 확인하지 않는다. 하나의 서버 측 트랜잭션으로 처리하고 실패와 재시도를 기록한다. 취소 알림도 결정해 구현한다.
3. **권한과 저장소:** 실제 Supabase의 RLS·Storage 정책, 서비스 역할 키 노출 여부, 관리자 권한과 관리자 다중 인증을 별도 테스트 계정으로 검증한다. 저장소 정책이 있다고 해서 운영 설정이 동일하다고 가정하지 않는다.
4. **신청 복구:** 계약서 업로드·이력·알림 실패 시 불완전한 신청이나 중복 제출이 생기지 않도록 상태와 복구 방안을 설계한다.
5. **개인정보:** 임대차계약서와 계좌정보의 수집 목적·범위·보관 기간·삭제 및 이용자 권리를 정하고, 실제 운영자 정보·수탁자·국외 이전 여부를 확인해 개인정보 처리방침을 완성한다. 현재 `/privacy`는 안내용 초안으로, 완성된 법정 방침이라고 볼 수 없다. [개인정보 보호법 제16조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335671).
6. **인증:** 이메일 인증 상태, 계정 탈취·비밀번호 재설정, 로그인 시도 제한과 관리자 MFA를 점검한다. 전화번호는 회원가입·신청의 필수 여부와 해외 번호 및 인증 가능 여부를 파트너 요건과 수집 목적에 맞춰 결정한다.
7. **파일과 계좌:** 계약서 업로드 타입·내용·크기 검증, 악성 파일 방어, 보존 및 삭제, 계좌번호 암호화·키 관리·접근 로깅을 설계하고 실제 접근 경로를 검증한다. 화면 마스킹만으로 데이터베이스 암호화가 되는 것은 아니다.
8. **결제 보안:** 카드번호·CVC를 자체 서버나 로그에 저장하지 않는 외부 결제창 방식을 우선 협의한다. 외부 위탁만으로 모든 책임이 사라지는 것은 아니므로 적용 범위를 매입사·결제 파트너와 확인한다. [PCI SSC 안내](https://www.pcisecuritystandards.org/faqs/does-pci-dss-apply-to-merchants-who-outsource-all-payment-processing-operations-and-never-store-process-or-transmit-cardholder-data/).
9. **운영:** 고객 문의·분쟁·환불·오송금·결제 실패·장애 대응, 이상 거래 탐지, 접근 기록 및 보존, 백업 복원 시험과 사고 통지 체계를 마련한다.
10. **표현:** 실제 서비스가 제공되지 않는 동안 테스트라는 사실을 명확하게 유지한다. 확정되지 않은 송금·제휴·실적·안전성을 보장하지 않는다.

## 3. 개발 순서

1. 파트너 질의서와 자금 흐름·수수료 구조 확정. 실제 금융 API는 연결하지 않는다.
2. 별도 개발용 Supabase 및 테스트 사용자 2명·관리자 1명 준비. 운영 데이터와 분리한다.
3. 서버 측 신청 검증, 제출 중복 방지, 신청/파일 실패 복구를 구현한다.
4. 상태 변경·이력·알림을 한 트랜잭션으로 구현하고 상태별 허용 전이를 제한한다.
5. 사용자 간 조회 차단, 관리자 권한, 파일 직접 접근, 파일 크기·종류, 모바일 접근성을 테스트한다.
6. 법무·금융 파트너 확정 후 운영 데이터 취급과 고객 보호 체계를 구현한다.
7. 파트너 샌드박스에서 승인·실패·취소·환불·정산 대사 및 장애 복구를 검증한다. 실제 API 전환은 별도 출시 승인 후 진행한다.

## 4. 파트너에게 물어볼 질문

- 월세를 카드로 결제하고 별도 가입하지 않은 임대인 계좌로 지급하는 구조를 지원하고 계약상 허용하는가?
- 누가 가맹점이고, 누가 결제대금을 수령·보관·이체하는가? 각 주체의 등록·면제 근거는 무엇인가?
- 임대차계약 및 임대인 계좌 명의의 검증, 임대인 통지 또는 동의가 필요한가?
- 해외 발급 카드, 외국인 본인 확인, 환율·해외 카드 수수료 및 전화번호 요건은 무엇인가?
- 신청 취소, 승인 후 취소, 환불, 차지백, 오송금, 정산 실패의 처리 주체와 기한은 무엇인가?
- 사용자에게 표시할 요금 항목, 과금 주체, 총액과 계약 조건은 무엇인가?
- 웹훅 서명·중복 처리, API 키 관리, 장애 대응, PCI DSS 검증 범위는 무엇인가?

## 5. 현재 점검 범위와 한계

- 코드는 정적 검토했다. 실제 운영 데이터베이스 정책·권한, 결제 파트너 계약, 실제 금융 API 실행 가능 여부를 종합 검증한 것은 아니다.
- 기존 브라우저 확인에서 관리자 겸 신청자 계정의 계약서 미리보기와 취소 이력을 확인했다. 서로 다른 일반 계정 간 접근 차단, 신규 제출부터 승인·반려 알림까지는 별도 테스트가 남았다.
- `app/applications/new/page.tsx`의 월세 금액 양의 정수 검증을 추가했다. 이 검증은 브라우저 편의 기능이며 서버·DB 검증을 대체하지 않는다.
